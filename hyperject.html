Hyperject

Unified breach-and-attack-simulation (BAS) tool for telemetry-injection techniques — plus the detection half of the loop.

Built by tjnull for Church of Malware telemetry research MIT v0.8.0

What it is

Hyperject consolidates the per-target PoCs from this research into one config-driven package with a plugin module system. Each target is its own self-contained file — 37 modules covering the telemetry ecosystems triaged in this disclosure. It sends injection techniques (basic / bulk / large / covert) to a target and classifies each response as EXPOSED, auth-required, or rejected. The detect side reviews an ingest log and confirms which techniques got through — the blue-team half of the loop.

Two clearly separated areas in the repo:
  • source-files/ — original PoC scripts, untouched reference. The tooling never reads, writes, or imports from here.
  • hyperject-main/ — the hyperject pipx-installable package. No built-in targets or credentials; runtime files (config.json, results.json, ingest.log.jsonl) are generated in the directory you run from.

Safety model

  • No built-in targets or credentials. Every endpoint and key comes from your config.json; the tool refuses to run against placeholder values.
  • Point it at the built-in mock collector (default) or an authorized lab range you control — never at third-party production infrastructure.
  • hyperject run --dry-run builds and prints payloads without sending anything.
  • Intercepting proxy passthrough, request/response middleware, and a host allowlist safety guard included.

This site hosts no third-party targets and no credentials. Use Hyperject only against systems you own or are authorized to test.

Quick start

pipx install ./hyperject-main
hyperject mock --port 8080 &        # 1. safe local target
hyperject init                      # 2. scaffold config.json from discovered modules
hyperject run --dry-run             #    preview (no traffic)
hyperject run                       # 3. generate injection traffic, record verdicts
hyperject detect ingest.log.jsonl   # 4. confirm every technique is detected

Commands: run · list · init · validate · mock · detect · capture · export. Full reference in the wiki.

How it pinpoints telemetry-injection flaws

Hyperject automates the exact recon loop this research used — then makes the result reviewable, repeatable, and defensible:

  1. Probe the boundary. Each module crafts real protocol-valid events (JSON, form, pixel, OTLP/protobuf — per-format rows) against one target endpoint, using your config keys. --dry-run prints every payload before anything is sent.
  2. Classify the answer. Every response is scored: EXPOSED = accepted injected telemetry with no required auth; auth-required = 401/403 (secure); rejected = other. The verdict lands per target and per format — so you see which encoding is the open one, not just that a host answered.
  3. Grade the techniques. Four payload grades — basic (single event), bulk (flood/volume), large (oversized payload), covert (data hidden in a telemetry field, e.g. C2 simulation) — expose whether the ingest accepts only clean events or tolerates abuse-shaped ones.
  4. Capture the evidence. Full request/response transcripts (JSON / JSONL / HAR / pretty), live colorized streams, and saved responses — the raw material for a defensible disclosure file, ready for canary tracing with the vendor.
  5. Close the loop (blue team). Point detect at the endpoint's ingest log and confirm each technique is caught — turning the same probes into detection tests. The built-in mock collector and host-allowlist middleware make this safe to run locally.

One caveat the tool is built around: a verdict of EXPOSED means the ingestion boundary accepted the event — it does not by itself prove storage, trusted use, or downstream impact. That boundary is exactly the line this site's whitepaper draws.
